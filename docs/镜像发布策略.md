# 镜像发布策略（镜像 tag 对齐 git tag）（v0.6.2）

> 与 [ADR-048](ADRs/048-ghcr-oci-image.md) / [ADR-049](ADRs/049-supply-chain-evidence-chain.md) 对齐。
> 本章是「镜像 tag 对齐 git tag」原则（决策 #49）的成文版：**GHCR 镜像 tag 永远等于 git tag
> 字符串本身（保留 `v` 前缀）**。

## 1. 映射规则

| Git（tag） | GHCR（镜像 tag） | 示例 |
|---|---|---|
| `v0.6.N` | `ghcr.io/chenjx12/ebpf-container-guard:v0.6.N` | `v0.6.2` → `...:v0.6.2` |

- 每次推送 `v*` git tag 都会触发 `release.yml`：构建并推送**同名同字符串**的镜像 tag（`v` 前缀保留、不剥离）。
- `latest` 每次发版后指向最新 release，**它不是版本号**，只表示"最近一次"。
- tag 必须小写（Docker registry 约束）。GitHub 仓库主是 `Chenjx12`（大写），而 GHCR 仓库是
  `ghcr.io/chenjx12/ebpf-container-guard`——workflow 用 `${GITHUB_REPOSITORY,,}` 自动转小写。

## 2. 该拉哪个 tag？

| 场景 | 拉取 | 原因 |
|---|---|---|
| 演示 / 秋招作品 / 毕设答辩 | **固定版本 tag**（`v0.6.0`、`v0.6.1`……） | 行为确定；`v0.6.0` 是永久保底安全网 |
| 尝新 | `latest` | 随版本移动；**不可复现的演示不要依赖 latest** |
| K8s DaemonSet | `deploy/k8s/daemonset.yaml` 里的镜像引用 | v0.6.x 内单独切换 GHCR |

## 3. git tag ≠ GitHub Release（决策 #48 教训）

tag 存在只说明 tag 存在。**Release（含附件）**由 workflow 创建，发完必须靠
`published_at` 确认。**证据在 release 附件上，不在 git tag 里。**

## 4. 每版 release 附的供应链证据（v0.6.2 起）

| 附件 | 证明什么 |
|---|---|
| `sbom.<tag>.cdx.json` | SBOM（CycloneDX）——镜像里有什么 |
| `trivy-report.<tag>.json` | 镜像层漏洞扫描（完整 JSON） |
| `trivy-fs-report.<tag>.json` | 依赖层扫描（仓库：requirements.txt / Dockerfile / 源码） |

两层扫描**各自独立设门槛**（severity `CRITICAL,HIGH` + `ignore-unfixed`），过了才允许发布；
报告本身可下载可核查——不是贴个徽章就算数。

## 5. 每次发版后的验收清单

1. GitHub Release 存在且 `published_at` 已设置（决策 #48）
2. 上面三个附件全部挂载且可下载
3. `docker pull ghcr.io/chenjx12/ebpf-container-guard:<tag>` 在注册表认证下成功\n   （该包需要注册表认证——匿名 `manifests/<tag>` GET 返回 401，无读权限的 token\n   返回 403；**pull 成功才是 tag 存在且可读的真实证据**）
4. README「镜像快速开始」照做能复现：pull → run（特权参数）→ 3 步内面板可开、读到真实事件
