# ADR-054: 行为日志可校验化——哈希链、轮转修复与落盘路径优化

## 状态
Accepted (v0.6.6)

## 背景

v0.4.x 的 `behaviors.log` 是裸 JSONL：一行一个事件，好坏不论。它能回答"发生了什么"，
但回答不了取证场景最基本的三问 —— **证据有没有被改过、有没有被删过、还在不在**。

三处硬伤：

1. **无完整性保护**：整行删掉、改一个字节，事后无从发现。
2. **保留期写死 7 天**：`DEFAULT_RETAIN_DAYS` 没有配置入口，`main.py` 传参也没有。
   取证场景下事故往往几周后才立案，7 天等于没有。
3. **两个会直接丢证据的缺陷**（读代码时发现，此前未暴露）：
   - `_maybe_rotate()` 用 `os.rename` 改名到 `behaviors.log.<日期>`，**同名会覆盖**。
     一天内写满 `max_bytes` 触发两次轮转，第二份就把第一份顶掉。
   - `_cleanup_old()` 用 `rsplit('.', 1)` 取日期段。文件名一旦加序号就 `ValueError`，
     异常被 `except ValueError: pass` 吞掉 —— **旧文件永远不删**。

现有 `logs/` 里 `2026-09-17`（18MB）、`2026-09-18`（29MB）都没到 50MB，
所以覆盖缺陷一直没被踩到。**一旦放开压测或调小 `max_bytes`，证据就没了。**

## 方案

### 1. 日志格式 v2：链式哈希

每条记录追加三个字段（`LOG_FORMAT_VERSION` 1 → 2）：

```json
{"version":2,"seq":123,"prev":"<上一条 hash>","timestamp":"...",...原有字段...,"hash":"<sha256>"}
```

- `hash = sha256(prev + body)`，`body` 是去掉 `hash` 后的紧凑 JSON
- `seq` 单调递增、跨文件连续；首条 `prev` 为 64 个 `0` 的创世值
- **扁平结构**：新字段是加在顶层，`dashboard`/`server` 读取端不受影响

### 2. 规范化：只序列化一次

```python
body = _build_body(entry)                       # 紧凑 JSON，键序 = 插入序
digest = sha256(prev + body).hexdigest()
line = body[:-1] + ',"hash":"' + digest + '"}\n'  # 追加而非二次序列化
```

校验端用 `json.dumps(rec, ensure_ascii=False, separators=(',',':'))` 复现同一字节串，
**不用 `sort_keys`** —— 字典由写入端按固定顺序构造，`json.loads` 会保留文件中的顺序。

### 3. 链的连续性（三种情况都要接得上）

| 情况 | 处理 |
|---|---|
| 正常轮转 | 内存里的 `_last_hash` 直接作为新文件首条的 `prev` |
| 进程重启 | 从**最新文件**的最后一个合法行恢复 `seq`/`hash`（尾读 64KB） |
| 崩溃半行 | 向前回溯到最近合法 JSON；校验端遇到解析失败报 `PARSE_ERROR`，**不静默跳过**（否则可用"写坏一行"来隐藏篡改） |

轮转文件名带序号：`behaviors.log.2026-11-14.001`、`.002` —— 从根上消除覆盖。
`_cleanup_old` 改为正则匹配，同时兼容历史无序号文件名。

### 4. 两种防伪模式

纯哈希链有个理论缺口：**攻击者改了记录，把整条链重算一遍照样能过**（代码开源）。

| 模式 | 机制 | 防什么 | 代价 |
|---|---|---|---|
| `hash`（默认） | `sha256(prev+body)` | 误删、误改、局部篡改 | 重算链可伪造 |
| `hmac` | `HMAC-SHA256(key, prev+body)` | 上述 + 重算链伪造 | 第三方无密钥无法独立验证 |

密钥 `/etc/ebpf-guard/chain.key`（32 字节，0600）。**可验证性与防伪性不可兼得**，
这是取证系统的固有取舍，不是实现缺陷。

### 5. 校验器 `tools/verify_chain.py`

逐行检查四件事：可解析 → `prev` 衔接 → `seq` 连续 → `hash` 正确。
文件顺序按 `(日期, 序号)` 升序，活跃文件最后。发现首个异常即定位到**文件名 + 行号**，
并说明"后续 N 条链全部失效"（这正体现哈希链的价值）。退出码 0/1，可进 CI。
遇到 v1 文件报 `SKIP` 并**重新自举**期望值，不阻断后续 v2 文件的校验。

### 6. 落盘路径性能优化（压测暴露）

| 优化 | 前 | 后 |
|---|---|---|
| `flush_interval` | 0.5s | **0.1s** |
| 单条序列化 | `json.dumps` 7–10µs | **手写模板 4–5µs** |

手写模板必须与 `json.dumps` **逐字节一致**，否则校验端重算的哈希全部对不上。
三重保险：类型守卫（非预期类型回落）、转义扫描（引号/反斜杠/控制字符回落）、
fuzz 单测（500 例随机串 + 边界用例断言两种实现等值）。

## 踩坑

- **`os.rename` 静默覆盖**：轮转不是"改名"而是"改名到可能已存在的名字"，
  POSIX 下不报错直接顶掉。带序号命名是最小改动且彻底。
- **`rsplit('.', 1)` 取日期**：加序号后取到的是 `001`，`strptime` 抛错被吞，
  清理逻辑静默失效 —— 表现为"日志目录无限增长"，很难联想到清理代码。
- **p95 尖峰的归因错位**：最初怀疑哈希拖慢消费，实测哈希只占 0.71µs/条；
  真正的元凶是 0.5s 一次的批量 flush 阻塞 ringbuf 消费者。`flush_interval`
  降到 0.1s 后 **p95 从 378ms 降到 20ms**。
- **`json.dumps` 是真正的热点**：7–10µs/条，是哈希的十倍以上。这类"看起来
  无害的标准库调用"才是吞吐上限的决定因素，凭直觉优化哈希等于白忙。
- **校验器遇到 v1 文件会"冻结"后续**：最初把 legacy 文件当成致命错误处理，
  导致混入一个旧文件后整份日志都不再校验。改为跳过 + 重新自举。
- **跨重启续链必须读磁盘**：只靠内存状态会在重启后让 `seq` 归零、链断裂，
  而单测恰好不会覆盖（同一个实例内写）。补了"重启后接续"的用例才暴露。

## 后果

**能力**

- ✅ 日志的增、删、改均可检出并定位到行号；跨文件、跨重启链连续
- ✅ 篡改检出 100%（哈希链的天然属性）
- ✅ 取证模式保留期 90 天，普通模式 7 天，均可在 `monitor.yaml` 配置
- ✅ 15 万条真实日志（跨两个文件）实测链完整

**性能**（k3s 停、4 核 VM）

| 速率 | 丢包 | p50 | p95 |
|---|---|---|---|
| 6000 ev/s | 0% | 15ms | 41ms |
| 8000 ev/s | 0% | 14ms | 144ms |
| **10000 ev/s** | **0%** | **12ms** | **21ms** |
| 12000 ev/s | 4.79% | 177ms | 465ms |
| 15000 ev/s | 17.03% | 656ms | 840ms |

- 稳定上限由约 4000 ev/s 提升至 **10000 ev/s**（2.5x）
- 每次记录新增约 110 字节（`seq`/`prev`/`hash`），文件体积约 +45%

**代价**

- ❌ 纯 hash 模式下，能重算整条链的攻击者仍可伪造（需 hmac 模式）
- ❌ 默认 7 天保留期对取证仍偏短，须显式切到取证模式
- 📝 校验是离线工具，未接入面板（下一步可做成「证据包导出」按钮）
