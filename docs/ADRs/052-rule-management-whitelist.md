# ADR-052: 规则管理闭环 + 临时白名单（rules.yaml 单一权威源统一重写）

## 状态
Accepted (v0.6.5) — 2026-09-08 单机 e2e 验收通过（登录 → 规则增删改 →
白名单增删 → 整文件 YAML 始终可解析）+ 179 项单测 + 渲染级门禁 66/66 后转正。

## 背景
bp_v06x v0.6.5 = 「**规则管理 + 白名单**」。此前规则只可**追加**（`POST
/api/rules`），架构上存在两个缺口：

- **规则不可改不可删**：误录入、命中率差的规则只能留在 rules.yaml，
  运维无法收敛规则集
- **告警只能全量压**：对「已知正常的容器 / 命令」没有细粒度临时豁免手段，
  只能全局关检测。dismissed(误报) 与 ignored(已知豁免) 语义混在一起，
  AI 基线学习分不清「此容器此行为正常」vs「已知风险豁免」

同时在 e2e 测试中发现一个**深层裂缝**：rules.yaml 是 server 与 dashboard
共用的**单一权威源**，但两份 `append_rule_to_yaml` 都是「行尾拼一个
`  - name:` 块」——对**已存在多条规则**的缩进风格文件没问题，可一旦
文件被 `update_rule/remove_rule` 用 `yaml.safe_dump` **全量重写为列0风格**，
行尾 `  -` 就被解析为上一规则的**嵌套块**，整文件不可读 → 检测规则全部
失效。单测只覆盖「空文件追加」，漏掉真实场景。

## 方案

### 规则管理闭环（API）
- `PUT /api/rules/{name}` 按名改、`DELETE /api/rules/{name}` 按名删
  （write_op 角色）；全量重写 rules.yaml 且**保持条目顺序**，热重载 3s 生效，
  改动全量写 rules_audit.log 溯源
- 入库前置 normalize + schema 校验与 append 完全一致（同一规则引擎管线，
  保证改后仍可被检测层消费）

### 临时白名单（规则页子区）
- `POST /api/whitelist` / `DELETE /api/whitelist/{id}`；`kind=comm|container` +
  `valid_until` **到期自动失效**恢复告警；同 match **幂等**不重复入库
- guard 检出层命中检测时查 `whitelist_active_until`，有效期内抑制该事件告警
- 语义分离：白名单留痕区分 **dismissed(误报) / ignored(已知风险豁免)**，
  分两类记录供 AI 基线学习——「该容器此行为正常」vs「已知攻击豁免」是
  两种不同的事实，混存会让基线学歪

### rules.yaml 单一权威源 → 全量重写统一
- 修复：`append_rule_to_yaml`（server **和** dashboard 两处）改为
  **read-modify-dump 全量重写**，与 update/delete 同构——无论当前文件是
  缩进风格还是列0风格，输出恒定可解析，不会再出现混合缩进断裂
- 回归测试补「向**非空**文件追加」场景（旧测试只测空文件，故漏网）；
  同时断言新旧规则并存且原规则字段不被破坏

## 后果
- ✅ 规则集可收敛（改/删），改动全链路留痕延续
- ✅ 细粒度临时豁免：容器级/命令级抑制替代「全局开关检测」，到期自动恢复
- ✅ dismissed/ignored 分流让 AI 基线学习的正负样本边界清晰
- ✅ 共享 rules.yaml 的两套写路径收敛为同一种语义，YAML 断裂类事故
  （整文件不可读 → 全部规则失效）在结构上不可能再发生
- ❌ 全量重写在文件大时略慢（当前 12 规则，可忽略）；已确认的并发
  写场景仍由「两面板不同时编辑」的运维约定兜底
- 📝 白名单与 decisions.log 的 ignored 是两条独立实现（guard 检出层查
  whitelist，面板判决走 decisions）——语义同源但落点不同，v0.6.7 六层
  审计统一时需合并口径

## 后续修复（v0.6.5.1，2026-09-17）

HTTP 端到端（`tests/integration/rules_whitelist_e2e.py`）首次跑通时，在**白名单
边界**探到两个缺陷并修复：

- **过期不可续期**：`whitelist_add` 的幂等分支只比对 `kind+match`，不看到期 →
  过期条目永久占位。改为**仅仍有效的条目幂等**，已过期则用原 id 续期
  （审计记 `renew_whitelist`）。
- **非法 `valid_until` fail-open**：解析失败被当作「永不过期」→ 一个写坏的
  时间戳让白名单永久抑制告警。改为 **fail-closed**：`whitelist_parse_until`
  统一解析，非法按「已过期」处理，API 层校验返回 400（空串仍= 永久）。

**教训**：「到期自动失效」这类时间语义必须同时管住**写入口**（格式校验）与
**读出口**（解析失败必须 fail-closed）——只修一处会留下 fail-open 与永久占位
两条裂缝。
